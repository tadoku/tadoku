Next.js or TanStack Start:
which router, exactly?

“Next versus TanStack” hides four materially different choices. This guide compares the router architectures—not their logos—and maps each one to Tadoku’s current Pages Router codebase.

Short answer

If Tadoku moves to TanStack Start, use file-based routing for the application and reserve code-based or virtual routes for rare generated-route cases. Do not migrate to Next App Router merely as an intermediate step.

The four choices

Two frameworks, four routing models.

Pages Router and App Router share the Next.js name but have different data, layout, rendering, and navigation models. TanStack’s file- and code-based options share one route tree and runtime; the difference is how that tree is declared.

Next.js Pages Router

pages/logs/[id].tsx
Current state
  • One route per file, with dynamic and optional catch-all filenames.
  • Data arrives through getServerSideProps, getStaticProps, or global getInitialProps.
  • Layouts are application conventions such as getLayout, not a nested route primitive.
  • router.query mixes path and search values as broad string/array types.
  • Lowest immediate migration cost; weakest fit for typed URL state and nested route lifecycles.

Next.js App Router

app/logs/[id]/page.tsx
Next-native rewrite
  • Folder segments plus special files for page, layout, loading, error, not-found, and route handlers.
  • Nested layouts preserve state; parallel and intercepting routes support advanced composition.
  • Server Components are the default; interactive components opt into client boundaries.
  • Params get generated route-aware helpers, but search params still need application validation.
  • Best when RSC, streaming, and the modern Next.js ecosystem are explicit goals.

TanStack Start: file-based

routes/logs/$id.tsx
Recommended TanStack path
  • Files generate a typed route tree through the bundler plugin or Router CLI.
  • Params, links, navigation, search schemas, loader data, and route context share one inferred contract.
  • Nested, pathless, and non-nested layouts are explicit route primitives.
  • beforeLoad, loaderDeps, and loader make route lifecycle and preloading visible.
  • Best default for Tadoku if the Start migration proceeds.

TanStack Start: code-based

createRoute({ path: '$id' })
Specialized option
  • The same router capabilities, declared and assembled manually as a route tree.
  • Useful when routes are generated from configuration, plugins, or domain manifests.
  • Parent relationships and child arrays are explicit, which can aid metaprogramming.
  • More verbose and easier to misassemble than generated file routing.
  • TanStack’s own docs do not recommend it for most applications.

Repository implications

The router files are not the hard part.

The route syntax changes are mostly mechanical. The migration risk sits in global session hydration, shared UI navigation, URL-state behavior, and absent regression tests.

01 / SESSION

Three global SSR hooks

webv2, auth, and admin hydrate Ory sessions through _app.getInitialProps. App Router and Start require different request-to-route context designs.

02 / URL STATE

29 dynamic route files

Twelve web routes use optional catch-all pagination. TanStack’s search schemas offer a clear improvement, but changing canonical URLs must not be bundled into framework parity.

03 / SHARED UI

50 router-coupled files

The apps and shared ui package import next/router. Introduce a small navigation adapter before moving any app to avoid maintaining two component libraries.

04 / DATA

90 query/mutation calls

Routing and server data are not the same migration. Keep React Query v3 stable initially; integrate loaders around it and upgrade Query separately.

05 / TESTS

No app test/spec files

Build route, metadata, status, and auth journey snapshots before translating behavior. Otherwise the new router becomes the accidental specification.

06 / DEPLOYMENT

Independent hostnames help

Admin, auth, and webv2 can cut over independently at ingress. That makes either App Router or Start safer as a per-app migration than an in-place big bang.

Decision guide

Choose the architecture you actually want.

Do not select App Router merely because it shares a package name with the current stack. Its Server Component, caching, data, and layout model makes it a real migration with its own benefits and costs.

When minimizing change wins

Stay on Pages Router—for now

Upgrade dependencies, add tests, neutralize shared UI, and remove global coupling. This is a valid stabilization choice, not a long-term routing improvement.

When server-first React wins

Move directly to App Router

Choose this only if the team explicitly wants Server Components, segment streaming, parallel/intercepting layouts, and the modern Next.js model.

When typed interactive routing wins

Move directly to Start file routes

Choose this for typed URL state, explicit loaders/guards, interactive React defaults, and a generated route contract. Keep code-based routes exceptional.

Tadoku recommendation

File-based TanStack Start—conditionally, after the foundation spike.

It best addresses Tadoku’s real router pain: dynamic paths, pagination state, route-aware navigation, auth context, and loader boundaries. Use the generated file route tree for ordinary product routes.

Keep code-based or virtual routing available only for future route manifests or plugin-driven sections. If the Start spike fails its maturity/operations gate, remain on Pages Router and modernize there; do not spend an intermediate migration on App Router unless RSC becomes a product goal.
