Decision brief · 07 August 2026

Move deliberately,
not all at once.

TanStack Start is a credible architectural fit for Tadoku’s interactive, self-hosted React apps. The upside is real—but this repository is coupled to Next.js at the session, routing, shared-UI, and container layers. Approve a measured pilot before funding the full migration.

Recommendation
Conditional go: run a two-week foundation spike; defer the full portfolio commitment until its exit gate passes.
Confidence: medium-high

Repository snapshot

This is a portfolio migration.

Tadoku has four Next.js Pages Router apps, three of which are production services. The migration surface is modest in route count but unusually concentrated around global session hydration and shared framework-bound navigation components.

Pros & cons

The case is stronger for developer experience than for operations.

Because Tadoku already self-hosts Next.js in Kubernetes, “deployment freedom” is not a decisive benefit. The strongest gains are type-safe routing/search state, a Vite-based workflow, explicit loading and middleware, and a model that matches this codebase’s client-interactive React style.

Why move

Better fit for the code Tadoku already has

  • Interactive React is the default; this Pages Router codebase does not use React Server Components today.
  • Typed path params and validated search params directly address the 29 dynamic route files and pagination-heavy URLs.
  • Route loaders, route context, and middleware can replace ad-hoc router effects with explicit data/auth boundaries.
  • Vite should simplify the local toolchain and remove the standalone-output workaround in the current Dockerfile.
  • Node/Docker remains supported through Nitro, preserving the existing Kubernetes deployment model.

Why wait

Maturity and migration tax are material

  • TanStack’s own documentation still labels Start a release candidate; the Nitro/Vite integration is also documented as actively evolving.
  • The official Next.js migration guide assumes App Router, while Tadoku uses Pages Router and global _app.getInitialProps.
  • Shared UI components import next/link, next/router, and next/image, so one app cannot move cleanly without an adapter seam.
  • Auth regressions could affect login, cookie clearing, role gates, banned users, and cross-subdomain return URLs.
  • No existing app test suite means parity must be built before routes are translated.

What stays

Keep the migration boundary narrow

  • Do not redesign UI or modify Go services and API contracts.
  • Keep Ory Kratos and the existing cookie/domain topology.
  • Preserve every public pathname and HTTP status through the first cutover.
  • Keep React 18 initially; current Start package metadata accepts React 18 or 19.
  • Defer React Query v3 → TanStack Query v5 to a separate change unless compatibility forces it.

Cheaper alternative

Modernize within Next.js first

If the goal is primarily dependency health, not typed routing or Vite, upgrading Next.js and adding tests is lower risk. The framework switch earns its cost only if the team values TanStack Router’s type system and wants explicit control strongly enough to maintain a younger full-stack runtime.

Target shape

Change the web shell, not the product core.

Each hostname can move independently. A router-neutral UI layer and unchanged Go/Ory boundaries let old and new runtimes coexist while traffic switches at the ingress.

Acceptance criteria

The migration is done when behavior is boring.

A green build is necessary but insufficient. Use these gates for every production hostname, then keep the old deployment available through the rollback window.

URL parity

All legacy paths, redirects, status codes, query strings, and deep links match the baseline.

Session parity

Anonymous, user, banned, and admin journeys behave correctly on SSR and client navigation.

Security boundary

Every private API/server function authorizes independently; route guards are only the UX layer.

SEO parity

Titles, canonicals, robots, structured metadata, and rendered content match public-page snapshots.

Performance budget

No more than 10% regression in p75 SSR latency, web vitals, JS payload, or error rate.

Operational parity

Non-root container, health probes, logs, runtime configuration, and graceful shutdown work in Kubernetes.

Dual-runtime UI

The shared UI package contains no hard Next.js dependency outside an explicit adapter.

Rollback

Ingress can return to the warm Next deployment without a data migration or cookie invalidation.

Release evidence

One full canary window passes, and the baseline comparison is attached to the decision record.

Final call

Approve discovery, not destiny.

Proceed if typed routing, explicit data boundaries, and Vite are strategic priorities—and the team accepts maintaining a younger framework/runtime.

Stay on Next.js if the motivation is mainly “newer tooling,” if auth test fixtures cannot be built, or if the foundation spike cannot demonstrate a measurable workflow benefit.

Recommended next action: fund phases 01–03 only. The output should be a measured ADR and a production-shaped styleguide image, not a promise to migrate the other apps.
