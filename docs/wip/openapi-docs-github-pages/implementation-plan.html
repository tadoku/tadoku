Implementation plan · 9 August 2026

Publish Tadoku’s OpenAPI specs as a useful GitHub Pages reference

Extend the documentation site already deployed at tadoku.github.io/tadoku, generate navigable reference pages from the repository’s public OpenAPI contracts, and make drift or accidental internal-spec publication fail in CI.

Owner: Docs / API maintainers Delivery: 1 PR Risk: Medium No backend deployment
Chosen direction

One site, generated reference pages, an explicit public allowlist

Keep Docusaurus and the current GitHub Actions Pages deployment. Upgrade Docusaurus from 3.9.2 to 3.10.2, add docusaurus-plugin-openapi-docs and its theme at 5.1.3, and generate MDX into a dedicated API Reference section. Check the generated output into Git and verify it against the source specs during every relevant pull request.

Publish only four explicitly named api.yaml files. Do not glob the OpenAPI directories: the two internal-api.yaml files contain service-to-service URLs and are outside the public documentation scope. Hide the request-sending UI for the first release; cookie-authenticated calls from the GitHub Pages origin require a separately reviewed CORS and CSRF posture.

Benefits

  • Searchable, deep-linked API reference alongside existing architecture docs.
  • Specs remain the source of truth; CI detects stale generated pages.
  • No new host, deployment credentials, or Pages project is needed.

Trade-offs

  • The renderer adds dependencies and requires a small Docusaurus upgrade.
  • Generated MDX creates reviewable repository churn when a contract changes.
  • Interactive requests wait until browser auth security is deliberately designed.

Phase 0 · Baseline and safety contract

Freeze what must remain true

Sequential prerequisite · Small · Docs owner
  • Record the existing Pages URL, base path /tadoku/, and a smoke-test list of representative existing documentation routes.
  • Encode the six-spec inventory above in the implementation notes and obtain maintainer confirmation that the four public files are safe to expose.
  • Record the expected count of 68 public operations and add a negative assertion for /internal/v1/ and the internal service hostnames.
  • Capture a before-build of the current docs site so the Docusaurus upgrade can be checked for navigation or styling regressions.
Gate 0: Maintainers approve the four-file public allowlist; existing Pages routes and the expected operation count are documented.

Phase 1 · Reproducible docs toolchain

Move the docs build to pnpm and compatible pinned packages

Sequential foundation · Medium · Frontend/docs owner
  • Add packageManager: pnpm@10.10.0 to docs/package.json, generate docs/pnpm-lock.yaml, and remove docs/package-lock.json.
  • Upgrade all Docusaurus packages together from 3.9.2 to 3.10.2; pin the OpenAPI plugin and theme to 5.1.3 and include the theme’s required Sass plugin.
  • Use pnpm/action-setup@v6 plus actions/setup-node in deploy-docs.yaml, caching against docs/pnpm-lock.yaml; install with pnpm install --frozen-lockfile.
  • Run pnpm typecheck and pnpm build before adding generated API pages; compare the representative routes and visual baseline from Phase 0.
Gate 1: The current site builds with pnpm, typechecks cleanly, preserves /tadoku/, and the lockfile is reproducible in CI.
2
Phase 2 · API reference generation

Generate pages for the public contracts

Parallel lane A after Gate 1 · Medium · API/docs owner
  • Register four named plugin configurations in docs/docusaurus.config.ts; use exact file paths rather than directory globs.
  • Generate output beneath docs/docs/api/, one stable directory per service, grouping endpoints by OpenAPI tag and generating service overview pages.
  • Set hideSendButton: true, keep credential persistence disabled, and link each overview to its source YAML on GitHub.
  • Add api:generate and api:check scripts. The check regenerates all four references and fails on git diff --exit-code -- docs/docs/api.
  • Commit the complete generated output. Do not hand-edit generated MDX; improvements belong in the source OpenAPI files or committed wrapper pages.
  • Verify that repeated operation IDs such as ping remain isolated by service directory and yield unique routes.
Gate 2: A clean regeneration produces no diff, exactly 68 operations render, all four service overviews build, and no internal paths or hostnames appear in docs/build.
3
Phase 3 · Information architecture and reader guidance

Make the generated pages understandable

Parallel lane B after Gate 1; integrate after Gate 2 · Small · Docs owner
  • Add an API Reference top-level navigation item and compose the four generated sidebar slices in this order: Immersion, Content, Profile, Authorization.
  • Create docs/docs/api/index.md with a service map, production base URLs, version labels, source links, and a clear distinction between anonymous and cookie-authenticated operations.
  • Explain that the first release is read-only documentation: code samples are illustrative and request execution is intentionally disabled.
  • Replace the existing service-page links that point only to raw YAML with links to the rendered reference, retaining a secondary “View source spec” link.
  • Check desktop and mobile navigation, light/dark appearance, endpoint anchors, schema expansion, and copyable code samples.
Gate 3: A reader can reach each service reference in two clicks, understand its base URL and authentication model, and return to the existing service documentation without dead ends.
4
Phase 4 · CI and Pages delivery

Build on pull requests; deploy only from main

Parallel lane C after Gate 1; integrate after Gates 2–3 · Medium · CI owner
  • Extend the workflow path filters to the four allowlisted spec paths. Do not include wildcard paths that would silently publish future internal specs.
  • Run docs verification on pull requests touching docs, the workflow, or an allowlisted spec: frozen install, API regeneration/drift check, typecheck, and production build.
  • Add actions/configure-pages@v5 before artifact upload and use the current Pages artifact action; retain pages: write, id-token: write, the github-pages environment, and the serialized deployment group.
  • Condition the deploy job on a push to main or a manual dispatch so pull requests validate without publishing.
  • Upload only docs/build; fail before upload if generated docs drift, the static build fails, or the internal-spec negative check finds a match.
Gate 4: A spec-only pull request runs the docs checks, a pull request cannot deploy, and a main-branch test deployment reports the expected Pages URL.
5
Phase 5 · Release verification

Prove the public site matches the repository

Sequential release gate · Small · Reviewer + docs owner
  • Open the deployed site at https://tadoku.github.io/tadoku/api/ and smoke-test one anonymous and one authenticated operation page per service.
  • Check all existing baseline routes, the API navbar entry, four service overviews, endpoint deep links, source-spec links, and the custom 404 behavior.
  • Search the built artifact and the deployed site for internal-api, /internal/v1/, authz-api:8080, and profile-api:8080; every check must be empty.
  • Confirm the GitHub Pages environment records the deployment and that a subsequent documentation-only change replaces it successfully.
  • Document rollback: revert the docs/plugin/workflow commits and redeploy the prior Docusaurus artifact; no service or database rollback is involved.
Gate 5: All success criteria below pass against the production Pages URL and two maintainers sign off—one from API ownership and one from docs/frontend ownership.

Atomic delivery and parallel work

Commit 1 · Toolchain

pnpm migration, Docusaurus upgrade, compatible renderer dependencies, unchanged-site proof.

Commit 2 · Reference

Allowlisted configs, generated MDX, API landing page, sidebar and service links.

Commit 3 · Delivery

PR verification, spec triggers, Pages configuration, internal-spec guard and release checks.

Parallelization: after Gate 1, lane A can implement renderer/generation, lane B can draft the API landing page and link map, and lane C can prepare workflow conditions and negative checks. They merge only after their respective gates pass. No schema or data migration is involved.

Follow-up improvements this unlocks

  • Add Spectral or Redocly contract linting once a repository ruleset is agreed, then make it part of the same PR gate.
  • Improve info.description, tag descriptions, examples, error schemas, and deprecation notes in the source specs.
  • Publish release snapshots and a version selector when API versions begin to diverge from the current contracts.
  • Add site search indexing and API-reference analytics to learn which operations need better examples.
  • Design a separate, security-reviewed API explorer using a safe auth flow or proxy; do not simply enable credentialed cross-origin requests.
  • Optionally publish internal references to an authenticated site, using an independent allowlist and deployment target.
