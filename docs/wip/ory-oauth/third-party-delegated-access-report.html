Let third-party apps act for users—without ever seeing a password.

Add Ory Hydra as the delegated-authorization server. Use Authorization Code + PKCE, opaque access tokens, narrowly scoped public API routes, and Oathkeeper introspection so the existing Go services continue receiving the internal JWT format they already understand.

01 / short answer

OAuth is exactly the right mechanism; Hydra is the missing Ory component.

Kratos should keep authenticating the human. Hydra should issue revocable delegated credentials to a named third-party client. Oathkeeper should validate those credentials at the edge. Keto should keep enforcing global user status and resource permissions.

Recommended target

Ory Hydra + OAuth 2.0 Authorization Code with PKCE

For the reading-tracker example, the app requests only logs:write and, if it must publish later while the user is away, offline_access. The user approves those permissions on Tadoku. The app receives tokens—not the user’s password or Kratos cookie.

02 / architecture

Add Hydra beside Kratos—not in place of it.

Hydra deliberately does not manage users or passwords. Its login-and-consent app can reuse the existing Kratos browser session and pass the Kratos identity UUID to Hydra as the OAuth subject.

Kratos · who is the human?

Login, passkeys/passwords, MFA, recovery, identity traits, and browser sessions.

Hydra · what did they delegate?

Client registration, consent, scopes, grants, tokens, refresh, discovery, and revocation.

Oathkeeper · is this request allowed in?

Credential validation, scope/audience enforcement, and conversion to an internal JWT.

Keto/domain · may this subject do it?

Bans, roles, ownership, contest rules, and business authorization within Tadoku.

03 / end-to-end

What “Connect to Tadoku” should do.

This is the standard browser-based authorization code flow. The third party never renders a Tadoku password field and never receives a Kratos session cookie.

Developer gets a client ID

The developer can use a self-service “Create application” page. Tadoku records exact redirect URIs, client type, owner, privacy policy, and allowed scopes, then creates the Hydra client automatically. Manual approval is useful for an initial pilot or unusually sensitive scopes, but is not a protocol requirement.

User starts connection

The tracker creates a high-entropy state, PKCE verifier, and S256 challenge, then opens Tadoku’s Hydra authorization endpoint in the system browser.

Kratos authenticates

The Tadoku login/consent app checks the current Kratos session. If needed, it sends the user through the existing login/MFA experience.

User consents

Tadoku shows the verified app name, developer, exact permissions, plain-language background-access meaning, privacy links, and Approve/Deny actions. No scope is silently added.

Hydra returns a code

The browser redirects only to the registered URI. The client verifies state and exchanges the one-time code plus PKCE verifier at the token endpoint.

Tracker publishes

The client calls POST /api/v1/logs with Authorization: Bearer …. The access token is short-lived; the request body uses the existing log contract.

Oathkeeper enforces

The public route accepts Hydra bearer tokens only. Oathkeeper introspects the token, requires logs:write, verifies issuer/audience, and mints an internal JWT whose sub is the Kratos UUID.

User can disconnect

A Connected Apps screen revokes the Hydra grant/token family. Opaque-token introspection makes revocation effective immediately when gateway caching is disabled.

✓
The application can keep publishing without a password.

It uses a refresh token only when the user explicitly approved offline access. Refresh tokens rotate and remain confined to the client’s secure storage.

Registration can be low-friction

OAuth still needs a distinct client_id so Tadoku can bind redirect URIs, identify the app on consent and audit logs, apply per-client limits, and let users revoke one app without affecting another. The good product experience is instant self-service registration for ordinary scopes—not one shared anonymous client and not an email-based approval queue.

  • Initial pilot: create the first one or two clients manually.
  • Normal developer experience: a small authenticated developer page provisions Hydra through Tadoku’s backend.
  • Later, if needed: protected dynamic client registration can automate deployments. Avoid completely open registration.

Self-hosted Hydra needs Tadoku-owned screens

Yes—but most of the authentication UI already exists. Add challenge-handling routes to the current auth frontend rather than building another account system.

  • Login adapter: check the Kratos session and accept Hydra’s login challenge; redirect through the existing login page only when signed out.
  • Consent page: show the app and requested permissions, then approve or deny the consent challenge.
  • Logout/error routes: handle Hydra logout challenges and protocol failures.
  • Connected Apps: a Tadoku account page for reviewing and revoking grants.
04 / contract

Start with one permission and one public endpoint.

The safest launch is deliberately narrow. OAuth scopes describe what the user delegated to the client; the API must still derive the user ID from the validated token and apply normal domain rules.

Initial scope vocabulary

Grant only the smallest set needed by a client. Avoid a generic api, write, or wildcard scope.

logs:writeCreate reading/listening logs for the authenticated subject. It must never accept a caller-supplied user ID.
logs:readFuture, separate permission to read the user’s own private log history.
profile:readFuture, minimal stable profile fields. Do not bundle email unless genuinely needed.
offline_accessDoes not grant another API action. It asks Tadoku to issue a refresh token so the app can obtain new short-lived access tokens after the user closes the browser or signs out.
openidOnly if a client also uses Tadoku as an identity provider. Not required merely to publish a log.

Recommended token profile

Keep the credential exposed to third parties different from the credential trusted inside the cluster.

  • External access token: Hydra opaque token, 10–15 minute TTL.
  • Refresh token: opaque, rotated on use, replay/reuse detection enabled; begin with a 30-day idle and 180-day absolute grant policy.
  • Internal token: Oathkeeper-signed short-lived JWT containing sub, credential kind, OAuth client ID, scopes, issuer, and audience.
  • Audience: a stable Tadoku API identifier, checked at Oathkeeper.
  • Introspection cache: off for launch; if load later requires caching, use a short bounded TTL and a patched Oathkeeper release.

i
Plain-language meaning of offline_access

Without it, the tracker can publish only until its short-lived access token expires—roughly 10–15 minutes in the proposed profile—then the user must reconnect. With it, Hydra also gives the app a rotating refresh token. The app still has only logs:write; it merely retains that permission while the user is not actively on Tadoku. The consent screen should say “Keep publishing in the background,” not expect users to understand the protocol name.

05 / repository fit

The current design is close—but has two launch blockers.

The edge already converts Kratos sessions into Oathkeeper JWTs, and services already identify a user by the token subject. That makes Hydra integration unusually clean. The gaps are scope-aware public routing and profile-trait coupling.

fit

Oathkeeper already normalizes identity for services.

Every internal API rule uses cookie_session followed by the id_token mutator. Go services validate Oathkeeper JWKS and consume a unified user/service claim type. Hydra tokens can enter the same normalization point through oauth2_introspection.

fit

The write domain already derives ownership from authenticated subject.

LogCreate ignores any caller-supplied user ID and assigns req.userID from UserIdentity.Subject. That is the correct invariant for delegated writes and should remain unchanged.

services/immersion-api/domain/logcreate.go:77–100

blocker

Delegated tokens must not overwrite Kratos profile data.

LogCreate calls UserUpsert before every write. UserUpsert copies DisplayName and the gateway JWT’s issue time from the authentication context; the SQL updates when that time is newer. An OAuth-normalized JWT will not carry a fresh Kratos session, so an empty or stale display name could replace the canonical value. Refactor this before enabling the public route: profile synchronization should fetch Kratos server-side or preserve existing fields when delegated credentials lack authoritative traits.

blocker

Scopes need an explicit enforcement boundary.

The current UnifiedClaims model has no client ID, credential kind, or scope fields, and the broad internal Oathkeeper rules fall back to anonymous. Add an exact public rule for each method/path with Hydra introspection and required_scope; propagate client/scopes into the internal JWT for audit and defense-in-depth.

!
Do not “solve” the trait issue by embedding full Kratos sessions in long-lived OAuth grants.

That would duplicate mutable identity data, expose unnecessary PII through introspection, and still become stale. Treat the Kratos identity UUID as the stable subject; resolve mutable profile data from its source of truth.

06 / security profile

Build to today’s OAuth security BCP, not the 2012 minimum.

RFC 9700, published in 2025, requires PKCE for public clients and recommends it for confidential clients. It also deprecates unsafe patterns such as implicit access-token delivery and the resource-owner password grant.

01

Authorization Code + PKCE S256 only

Require PKCE for public, native, SPA, and confidential clients. Reject downgrade attempts and constant challenges.

02

System browser for native apps

Never allow embedded webviews to collect Tadoku credentials. Prefer claimed HTTPS redirects; support loopback/native redirects carefully.

03

Exact redirect URIs

No wildcards, fragments, or open redirects. Permit HTTPS in production, with only the RFC-defined native-app exceptions.

04

Opaque, revocable tokens

Clients treat tokens as opaque. Oathkeeper asks Hydra whether each token is active, unexpired, unrevoked, and correctly scoped.

05

Refresh rotation and secure storage

Rotate refresh tokens, detect reuse, revoke the family on compromise, and require native secure storage or server-side secret vaults.

06

State, issuer, and nonce

Clients bind transaction-specific state; verify issuer to prevent mix-up; use nonce when OpenID Connect is requested.

07

Consent is not a checkbox

Show a verified app identity, exact requested actions, offline behavior, data handling links, and prior grants; do not preselect additions.

08

Rate limits and audit events

Rate-limit authorization, token, and public API endpoints. Record client ID, subject, scope, outcome, and request ID—never tokens.

09

Operational revocation

Users, admins, and clients need revocation paths. Account deletion and client disablement must revoke all related Hydra grants.

!
Oathkeeper security gate

Before enabling oauth2_introspection, upgrade and pin Oathkeeper to the latest stable patched release, then review the current security advisories. Keep introspection caching disabled at launch; a prior official advisory covered cache-key confusion across introspection servers, so any later caching design must be reviewed against the selected release.
