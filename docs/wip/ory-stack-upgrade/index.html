01 / ANSWER

What would it take?

Yes: use a prepared big-bang Kratos cutover. It removes the unsafe mixed-version interval and concentrates downtime into backup, migration, pod readiness, and immediate verification.

Recommendation

Big bang is safer and faster than rolling Kratos.

The live Deployment uses RollingUpdate with maxSurge: 30% and maxUnavailable: 0. A plain version bump can migrate the shared database while the v0.13.0 pod still accepts writes. The cutover must explicitly prevent that overlap.

  • Control production firstAdd a tested Argo deployment hold. Do not change credentials or signing keys during the Ory migration.
  • Prove production contractsCover cookies, browser flows, five proxy rules, the service exchange, permission tuples, and the PostSync admin seed.
  • Pre-stage outside downtimeApprove the migration PR, prepare an unsubmitted runtime patch, pre-pull the exact image digest, restore the rehearsal database, and have rollback commands ready.
  • Freeze every old writerHold Argo and stop both the Kratos API and courier before the standalone migration begins.
  • Cut over immediatelyTake the final copy, migrate, deploy v26.2.0 with automigration disabled and Recreate strategy, then run focused smoke tests.
  • Harden secrets afterwardAfter the Ory verification gate, introduce Sealed Secrets with current values, then rotate every secret as separately verified follow-up work.

Do not use the chart's normal rolling path: Kratos v0.13.0 is not write-compatible with the v26.2.0 PostgreSQL schema. Keep chart automigration disabled and run the migration as an explicit Job only after all old writers are at zero. Keto v25.4.0 → v26.2.0 has no schema-file delta; Oathkeeper has no database.

Benefit

Shortest safe outage

All preparation happens while v0.13.0 is still serving. The unavailable interval contains only the final copy, up to 47 post-v0.13 migration versions, v26.2.0 readiness, and critical smoke tests.

Trade-off

Authentication is briefly unavailable

Oathkeeper depends on Kratos /sessions/whoami, so authenticated requests fail closed while Kratos is stopped. Blue/green on the same database does not solve this compatibility boundary.

Success criterion

≤5 minutes—or the measured truth

Approve the production window after one successful timed rehearsal. Target at most five minutes from last old writer to healthy v26.2.0; if rehearsal is slower, publish the measured duration instead of forcing the budget.

  • Keto subagent: confirm no pending schema migration from v25.4.0 → v26.2.0, then test tuple reads/writes and pagination behavior against both binaries.

Sequential production gate

Roll Keto, then Oathkeeper

Remove the lower-risk service changes before opening the Kratos maintenance window.

  • Keto: confirm clean migration status, then deploy chart 0.63.0 and app v26.2.0; no database mutation is expected.
  • Verify Keto permissions, tuple writes/deletes, pagination, OPL namespace, and deterministic PostSync seed.
  • Oathkeeper: deploy chart 0.63.0 and app v26.2.0 while retaining active signing material.
  • Verify all five proxy rules, forwarded headers, redirects, user JWTs, and the service-token exchange before advancing.
Exit gateKeto and Oathkeeper pass their complete immediate verification suites, with no unexplained Argo drift.
Sequential maintenance gate

Execute the Kratos big bang

Honor the standalone-migration rule without pretending the old runtime remains write-compatible.

  • Before the window, disable chart automigration, render the target with strategy.type: Recreate, pre-pull the exact v26.2.0 image digest, and prepare an unsubmitted runtime patch plus a waiting reviewer.
  • At the window, hold Argo and scale the Kratos Deployment and courier StatefulSet to zero; confirm no v0.13.0 pod remains.
  • Take the final logical copy, then deploy the standalone manually synced migration Job pinned to the v26.2.0 digest.
  • After the migration is deployed, base the runtime PR on updated main, merge/sync it immediately, and keep automigration disabled.
  • Run the critical smoke suite, restore normal traffic, then complete the wider checklist; restore the pre-migration database if the critical gate fails.
Exit gateMeasured downtime is within the rehearsed budget and all auth flows, existing sessions, new identity/session writes, courier delivery, and Oathkeeper session checks pass.
Post-migration follow-up

Introduce Sealed Secrets, then rotate all secrets

Keep secret-platform work outside the Ory migration blast radius and begin after the immediate Ory verification gate.

  • Deploy and verify the Sealed Secrets control plane independently of Ory version changes.
  • Move the current database, SMTP, backup, webhook, and Oathkeeper signing values into sealed resources without changing the effective values.
  • Verify all workloads, courier delivery, backups, permission checks, session validation, and JWT verification after the storage cutover.
  • Then rotate every secret category one at a time, preserving Oathkeeper verification overlap where required, and remove plaintext values from the active Git tree.
Exit gateAll live secret values are supplied through Sealed Secrets, every credential has been rotated and verified, and the active Git tree contains no plaintext secret material.

08 / ROLLBACK

Rollback is a data decision

Argo CD owns production desired state. Roll runtime configuration back with an explicit Git revision; treat Kratos and Keto rollback as database decisions.

GitOps boundary

Revert the pinned revision

Hold auto-sync, revert the exact Application/value commit, inspect the rendered diff, sync deliberately, and verify health. Do not rely on stale Helm release metadata for rollback.

Kratos data boundary

No old-binary rollback

Kratos v0.13.0 cannot safely resume writes after the v26.2.0 schema migration. Fix forward with v26.2.0 or restore the complete pre-migration logical database before bringing v0.13.0 back.

Keto + Oathkeeper

Runtime revert remains viable

Keto has no schema delta on this exact path, and Oathkeeper is stateless. Revert their chart/image through Argo while retaining tuple data, signing keys, and downstream token contracts.

Downtime versus recovery point: taking the final logical copy after writers stop preserves all committed data and currently costs about one minute. Taking it immediately before the freeze shortens downtime but creates a rollback data-loss window; use that option only if its measured RPO is explicitly accepted.

Hard stop: never run an untested down migration or restore selected tables in place. Restore each Ory logical database as a consistent unit, and account for the shared single-instance PostgreSQL blast radius.
