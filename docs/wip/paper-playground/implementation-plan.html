Design direction

Follow the brief’s communal reading log and contest noticeboard. Use the existing wordmark and Cut Meter; avoid generic marketing imagery. Put contest activity beside a concise invitation on the homepage. Use clear left alignment, restrained rules, and purposeful density for records and standings.

Phase 1 — finish and merge Paper

  • Integrate the current upstream main without discarding the existing review work.
  • Map Paper spacing to the Tailwind preset; retain useful default utilities, responsive variants, and distinct density tokens.
  • Remove the duplicate prefixed spacing API and migrate setup, examples, and class references. Keep standalone Paper components usable.
  • Validate package, source examples, consumer compatibility, boundaries, and style guide; run the workspace build.
  • Commit logical changes, create a reviewable pull request, pass CI, and merge into main.

Gate: the existing review and Tailwind improvements are merged, with relevant checks passing and any unrelated environmental limits recorded.

Phase 2 — build the unpublished app

  • Create the fresh app with Paper, its Tailwind preset, routing, fonts, sample session, theme and density controls, and a discreet scenario drawer.
  • Keep a durable inventory of source pages, scenarios, sample data, and unresolved product contracts.
  • Parallel lane A: Homepage and four Guide pages, including IA alternatives.
  • Parallel lane B: Leaderboard and Contests with their three scopes/collections.
  • Parallel lane C: Profile overview, activity log, admin workspace, and Log details.
  • Root integration: shared navigation, fixture identities, local persistence, logging and account affordances, app scripts, boundary checks, and build integration.
  • Implement meaningful transitions using local fixture data and React Hook Form. Clearly identify the app as sample data once in the review controls.

Gate: all 11 designs and named scenarios are reachable; links retain entity identity, interactions work, and app typecheck and build pass.

Phase 3 — iterate on real pages

  • Review every design in an actual browser at desktop and 390px, then exercise the state matrix and core journeys.
  • Inspect dark mode, comfortable/compact controls, CJK text, long values, empty states, overlays, and keyboard focus.
  • For each shared defect, write the failing regression check, assign its fix to an agent, and verify the passing result.
  • Promote only reusable fixes into Paper. Keep entity data, page arrangement, and product policy in the playground.
  • Update style guide source examples and class/prop guidance for any added or corrected public contracts.
  • Run relevant tests, lint, typechecks, consumer/package checks, and production builds after integration.

Gate: no unresolved severe usability defects in the implemented journeys; remaining questions concern documented product policy or production integration.

Phase 4 — final handoff

  • Commit the app and later Paper fixes in logical changes while keeping the app unpublished.
  • Capture representative browser evidence and a page-by-page verification ledger.
  • Publish the final report to Draft, with source provenance, routes, fixes, checks, and human decisions collected at the end.
  • Return the main merge identity, review branch/PR, report, and private preview if available.

Gate: the user can review every built page and understand exactly what changed in the design system without reconstructing the work from chat.

After this work

The completed app can support user comprehension testing, a data-contract review with the APIs, visual regression baselines, and a scoped migration of webv2. Those follow-ups should use measured feedback and explicit production policy decisions rather than extending this prototype into an accidental live application.
