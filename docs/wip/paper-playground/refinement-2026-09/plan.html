Make Paper feel like one application

The playground has working components, but the composition is unfinished. This pass fixes the shared alignment and gives every page a deliberate reading order, from the first action to the last supporting detail.

Scope: all eleven primary designs, their alternate states, and supporting forms and administration screens. Work stays on the local t3code/paper-visual-refinement branch in logical commits. No pull request or push.

What the first browser review shows

At a 1280 × 800 viewport, the logo begins 28 pixels before the content. The leaderboard stacks an introduction, tabs, round status, dates, filters, explanatory text, a personal banner and a caption before the first ranking row at approximately y770. The rankings should carry the page.

Design direction

Keep the established Paper identity and make it work for a reading community: clear records, calm prose, useful competition context. Use one shared content grid and explicit spacing between related groups. Spend visual emphasis on the page’s purpose, with secondary explanations set more quietly.

Type: Merriweather for page and editorial headings; Open Sans for body, controls and records; tabular numerals for scores. Keep prose below 72 characters per line. Use a compact page title on working screens and a more expressive opening on the home page.

Alignment: left-align text and use the same 1160-pixel maximum content area for the brand, main content and footer. Responsive outer gutters shrink from 28 to 20 to 16 pixels. Nested reading columns may be narrower while retaining the shared grid.

Critique of this direction: the warm canvas and serif are established Tadoku choices. The correction is in composition, not new decoration: a rankings sheet for comparison, readable editorial pages, an activity record for personal history and grouped forms for entry. Avoid uniform cards, redundant headings, repeated status labels and oversized metadata.

Phases and gates

1. Establish the shared frame

  • Capture the alignment failure and baseline leaderboard screenshot.
  • Unify header, main and footer gutters and verify desktop and mobile navigation.
  • Set a consistent heading, section and form rhythm.

Gate: brand, main content and footer edges match within one CSS pixel at desktop and mobile widths; navigation remains usable.

2. Refine independent page groups in parallel

  • Editorial agent: home and all four guide pages, including their alternate states.
  • Competition agent: leaderboard, contest collections, details, registration and contest forms.
  • Records agent: profile, activity, log detail and all administration sections.
  • Lead: activity entry/editing, settings, sign-in, contact and shared Paper improvements.

Gate: every route has a deliberate first screen, coherent grouping and readable mobile layout; desktop rankings are visible substantially earlier than the baseline.

3. Critique, verify and hand off

  • Inspect screenshots for all primary pages at desktop and mobile; inspect dark and compact modes and supporting interactions.
  • Exercise alternate states, forms, filters, row navigation and dialogs; fix visual and behavioral regressions.
  • Run relevant package/application tests, type checks, lint and builds.
  • Commit logical pieces locally and publish a report with page coverage, evidence and remaining decisions.

Gate: no unintended page overflow at 320, 390, 768 and 1280 pixels, no broken interaction in checked flows, relevant checks pass, and final screenshots have been inspected by an agent other than the implementing page owner.

Benefits and risks

The main benefit is a design system grounded in coherent real screens. The main risk is preserving all the sample application’s behavior while rearranging its markup. File ownership, existing interaction tests and browser checks keep those changes reviewable. Visual quality remains a judgment supported by screenshots, rather than a claim made from passing tests.

What this makes possible

Promote the useful page compositions into styleguide guidance, then review them with real content and real participant data. Any product decision that cannot be made from the current brief will be recorded in the final report without blocking independent refinement.
