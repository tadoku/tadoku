Scoring engine status + implementation plan · Phase 0 findings updated 18 August 2026

Dense listening is one rollout gate and one product control away

The new scoring engine is substantially complete and running in production shadow mode. Dense listening is missing because V2 records Listening as duration-only, while the existing dense modifier matches the legacy listening_dense_minutes amount unit. The shortest durable path is to finish the authoritative-engine cutover, model “high density” as an explicit dense tag, and expose that choice directly in the form.

Production engine: shadow Scope: Listening create + edit Delivery: one parity data migration, then rule/UI work Risk: medium until parity gate clears
Bottom line

Do not add the dense control before the engine becomes authoritative

The score-preview endpoint already evaluates the new engine even while production writes still use the interim scorer. Shipping a dense control first could preview 36 points for 60 dense minutes but persist only 24 points. The deployment order is therefore a correctness requirement: close shadow parity, enable authoritative scoring, activate the dense duration rule, then expose the form control.

Phase 0 execution finding

The evaluator is correct; the intentional Writing boost never reached version control

The observed mismatch was an 80-character Japanese Writing log. Legacy scoring used the production unit modifier 0.025 and persisted 2 points; platform rule-set v1 used 0.0025 and evaluated 0.2 points. The complete matrix shows the same exact 10× difference for every Writing unit: page 10 vs 1, sentence 0.5 vs 0.05, high-rate characters 0.025 vs 0.0025, and fallback characters 0.00833333 vs 0.000833333.

Chosen direction

Use the engine’s existing tag matcher; stop extending the legacy unit model

Add a stackable platform rule for Listening with score_source=duration_minutes, tag=dense, and rate=1.5. In V2 create and edit forms, show a first-class checkbox labeled High density, with helper text such as “Few breaks, for example an audiobook.” The checkbox adds or removes the normalized dense tag through react-hook-form. The live score preview then makes the effect explicit.

Benefits

  • Uses rule matching, normalization, previews, provenance, and contest fallback behavior that already exist.
  • Requires no database schema or data migration and no new API field.
  • Moves toward the ADR’s planned removal of listening_dense_minutes.
  • Preserves old clients: legacy amount + high-density-unit logs keep scoring as before.

Trade-offs

  • dense becomes a score-affecting tag and needs a clearly owned product meaning.
  • Published scores remain snapshots; old ambiguous duration logs cannot be identified safely for automatic repair.
  • Existing custom contests pinned to platform v1 will not silently inherit the new rule.
  • The platform rule-management API exists, but there is not yet a platform rule editor UI.

Legacy compatibility boundary

Do not rewrite existing dense-minute logs during the feature restoration

Existing dense Listening logs are explicit legacy amount/unit inputs: an amount measured with unit_key=listening_dense_minutes. Their score is already a historical snapshot. Activating platform v2 must not reinterpret or rewrite those rows. Instead, v2 is a strict superset of v1: it retains the existing amount + listening_dense_minutes modifier and adds the new duration_minutes + tag=dense modifier.

At dense-restoration launch

  • Leave existing amount, unit key, computed score, and provenance unchanged.
  • Continue accepting old clients and the ordinary legacy form.
  • Recognize a legacy dense unit as “High density” when displaying or editing the log, even if it has no dense tag.
  • Keep the amount-unit dense rule in every active platform version while any old writer remains.

When logging flow v1 is retired

  • First make V2 read and edit both legacy amount/minute logs and canonical duration/tag logs correctly.
  • Normalize any remaining legacy API writes in the backend so old clients cannot create new rows that miss duration or density metadata after the backfill.
  • After the V2 UI becomes the only site flow, ship a standalone additive data migration for historical time-primary minute logs, without recalculating their scores.
  • Only after old API clients are retired should a later standalone cleanup remove legacy write support, unit configuration, or obsolete tracking fields.

This conversion should cover all v1 minute-based logs for time-primary activities, not only dense Listening: copy the submitted minute amount into duration metadata, and additionally mark the explicit dense Listening/Speaking units with normalized density metadata. A dense legacy unit proves density intent, but conversion from floating-point minutes to integer seconds still needs an explicit rounding policy. Snapshot scores and provenance must never be recomputed merely because representation changes.
