Nothing is obviously broken—and that is why the gap is hard to name. The component set works, but the visual grammar and the documentation do not yet explain why it looks this way, when to use each choice, or what “correct” looks like across states.

01 / DIAGNOSIS

The missing layer is intentionality.

The site currently proves that components exist. A refined design system also communicates the decisions around them: hierarchy, behavior, boundaries, accessibility, and maturity.

Core finding

The library is presented as a kitchen sink, not as a decision-making tool.

That creates the feeling of “something missing”: pages are technically complete, but they do not create confidence, teach judgment, or express a distinct Tadoku point of view.

  • Examples lack a frameWhite previews sit directly on a near-white page, with no canvas controls, boundary, density, or state context.
  • Visual rules are implicitSquare controls, two-pixel bottom borders, shadows, spacing, and typography are individual styles rather than a named visual grammar.
  • Guidance is sparseMost entries are only a title, preview, and source. Users still have to infer when, why, and how.
  • Foundations are underspecifiedSeven utility colors and three type examples cannot carry a growing product system.
Component coverage7.2

Scores are directional heuristics, not compliance grades. They are intended to prioritize the next investment.

04 / RECOMMENDATIONS

Fourteen improvements, in order.

Start with the shared language and the documentation shell. Those changes improve every existing component before a large visual redesign is attempted.

P0 · NOW

Build confidence and coherence

Introduce semantic design tokens

The current palette names implementation colors (slate-500, lime-700) rather than user-interface roles. Add a stable layer for surface, text, border, action, focus, and status so product code does not choose raw hues.

  • Keep a primitive palette, but document it as an implementation detail.
  • Add light/dark aliases now even if dark mode ships later.
  • Give chart colors their own accessible categorical sequence.
--color-action-bg: #5f5ff5;
--color-action-hover: #5555e6;
--color-action-text: #ffffff;
--color-text-default: #202128;
--color-text-muted: #60636f;
--color-surface-canvas: #f6f6f8;
--color-border-subtle: #e2e3e9;
Impact Very highEffort MediumEvidence Color page

Define Tadoku’s visual grammar

The system feels unfinished because shape and depth are nearly absent: controls, previews, tables, and cards are predominantly square; buttons and inputs rely on a two-pixel bottom border. Decide and name the rules.

  • Suggested starting point: 6px controls, 10–12px cards/popovers, 16px modals.
  • Use one-pixel borders plus restrained elevation; reserve stronger shadows for overlays.
  • Keep Merriweather and violet as signature elements—the goal is refinement, not generic softness.
  • Define density, icon sizes, motion duration, and focus ring as tokens too.
Impact Very highEffort MediumRisk Needs review

Replace Showcase with a real documentation shell

The current Showcase offers a title and a binary Preview/Code toggle. Expand it into a consistent page anatomy: summary, status, examples, variants, states, usage, content, accessibility, API, and source.

  • Frame previews with a border, radius, neutral canvas, and compact toolbar.
  • Put Preview / Code / Props in tabs so changing one example does not move the page.
  • Add copy-code, deep-link, canvas theme, and viewport controls.
  • Keep prose outside the canvas so examples remain focused.
Impact Very highEffort MediumStart with Button

Make accessibility a component contract

Do a focused WCAG 2.2 sweep and document keyboard/screen-reader behavior alongside each component. Concrete issues already visible in source should become regression tests.

  • #6969FF is 4.15:1 on white, below the 4.5:1 threshold for normal text—including current button labels. A darker interactive violet such as #5F5FF5 reaches roughly 4.73:1.
  • Connect form hints/errors with aria-describedby and set aria-invalid; ensure every select/input has a matching id.
  • Use aria-current="page" for active breadcrumbs/navigation; Pagination currently labels its nav as “breadcrumb”.
  • Standardize visible :focus-visible, reduced-motion behavior, target size, and high-contrast support.
Impact CriticalEffort MediumAutomate axe + tests

Add a typed Button and LinkButton API

The documentation explicitly says buttons are CSS classes, so invalid combinations and missing states are easy. A component API makes hierarchy discoverable and provides one place for loading, icons, disabled behavior, and accessible semantics.

  • Use variants: primary, secondary, danger, ghost.
  • Use sizes and intent props rather than free-form class combinations.
  • Keep escape hatches for layout, but make the correct path the easy path.
  • Separate action buttons from navigation links while sharing visual recipes.
Impact HighEffort MediumMigration Codemodable
P1 · NEXT

Turn the site into a reference tool

Use one route per component, with search

Forms is over 4,200px tall and mixes six unrelated examples. Split it into Input, Select, Checkbox, Radio, Autocomplete, Tags, Textarea, and composed-form pages. Add keyboard-first search and a local page outline.

  • Provide a component index with category, description, and status.
  • Keep Foundation / Components / Patterns, but group components by job: Actions, Forms, Navigation, Feedback, Data display, Overlays.
  • Use stable anchor links for every example and guidance section.
Impact HighEffort MediumFirst split Forms

Show the whole state matrix

A default render rarely exposes the problems that make a system feel inconsistent. Document default, hover, pressed, focus, disabled, loading, error, empty, overflow, and long-copy states at a glance.

  • Use static state grids for visual review and interactive examples for behavior.
  • Include icon-leading, icon-only, long-label, and full-width cases.
  • Render at phone, tablet, and desktop widths—especially navigation and data tables.
Impact HighEffort MediumBenefit Fewer surprises

Rebuild the foundation pages

The Color page should show values, aliases, usage, contrast, pairings, and copy actions. Typography needs a full ramp—not only title, subtitle, and text link. Add spacing, radius, elevation, motion, iconography, and layout pages.

  • Give every token a name, value, example, purpose, and “do not use for”.
  • Separate body typography from display/editorial typography.
  • Document a reading column (about 65–75 characters) and a wider demo/data column.
  • Load fonts with document links/preload rather than a CSS @import.
Impact HighEffort MediumOwner Design + FE

Co-locate examples, metadata, and tests

The current custom guide can remain. Borrow Storybook’s best idea: each meaningful component state should be a reusable, named example near the component. Generate navigation, props tables, and status from that metadata.

  • Do not migrate tooling first; establish the documentation schema first.
  • Consider Storybook only if controls, autodocs, and visual testing save more maintenance than a custom renderer costs.
  • Reuse the same examples in docs, unit tests, and visual snapshots.
Impact HighEffort HighDecision After pilot

Add automated quality gates

A design system needs stronger checks than a product page because regressions multiply across consumers. Add visual diffs, accessibility scans, interaction tests, and token linting to the component workflow.

  • Start with Button, Input, Modal, ActionMenu, Navbar, and Pagination.
  • Snapshot all documented states and two responsive widths.
  • Fail changes that introduce raw color values outside the token layer.
Impact HighEffort MediumCoverage Top 6 first
P2 · SCALE

Make the system durable

Separate components, patterns, and experiments

“Logs overview” and “Logging flow v2” are valuable product patterns, but they currently sit beside production components without status. Create a Patterns section and mark exploratory work as experimental.

  • Components are reusable parts; patterns are recommended compositions; experiments are proposals.
  • Show which components a pattern uses and which product problem it solves.
Impact MediumEffort LowClarity Immediate

Add lifecycle and governance

Every page should show maturity, owner, last meaningful update, package version, and source. Publish contribution criteria and a lightweight review checklist.

  • Use three statuses: Experimental, Stable, Deprecated.
  • Require docs, accessibility notes, tests, and migration guidance before Stable.
  • Add “replaced by” links and removal dates for deprecations.
Impact MediumEffort LowPrevents Silent drift

Design for themes and user preferences

Even if Tadoku remains light-first, tokens should support dark surfaces, forced colors, reduced motion, zoom, and future brand modes. The preview canvas is the right place to expose those constraints early.

  • Test at 200% text zoom and narrow reflow widths.
  • Respect prefers-reduced-motion for modal, menu, toast, and loading animations.
  • Check charts and status colors without relying on hue alone.
Impact MediumEffort MediumTiming Token phase

Tighten the package boundary

Global element selectors and raw Tailwind utilities make it hard to know what is guaranteed by the design system. Define the supported public surface and make styles consumable without leaking accidental defaults.

  • Export tokens and a shared Tailwind preset; document global prerequisites explicitly.
  • Prefer component recipes over broad selectors for tables, links, form controls, and headings.
  • Audit package exports for duplicates, stale paths, and undocumented components such as Loading and VerticalTabbar.
Impact MediumEffort HighRisk Stage migration

06 / ROADMAP

A practical sequence.

Avoid a big-bang redesign. Build one polished vertical slice, validate the visual direction and documentation model, then scale it.

Week 1

Set the language

  1. Inventory current colors, type, spacing, radii, shadows, and states.
  2. Draft semantic tokens and contrast-safe interactive colors.
  3. Agree on the component page schema and maturity statuses.
Outcome: one shared vocabulary and fewer subjective reviews.
Weeks 2–3

Build the pilot

  1. Redesign Showcase and the page shell.
  2. Create typed Button/LinkButton APIs.
  3. Document Button, Input, Modal, and ActionMenu completely.
  4. Add accessibility and visual tests for their states.
Outcome: a believable end-to-end example of the future system.
Weeks 4–8

Scale deliberately

  1. Split Forms and Navigation routes; add search and page outlines.
  2. Rebuild foundation pages from token data.
  3. Cover the remaining components by usage frequency.
  4. Add governance, changelogs, and migration notes.
Outcome: a reference that can guide product work without tribal knowledge.
07 / GUARDRAILS

What to preserve.

Refinement should sharpen Tadoku’s identity, not sand it into a generic SaaS library.

Keep the editorial voice.

Merriweather gives headings a reading-focused character that fits Tadoku. Build a better scale around it rather than replacing it reflexively.

Keep examples grounded in the product.

The logging examples are a strength. Reclassify them as patterns and add decisions; do not replace them with abstract lorem ipsum.

Prefer fewer, clearer variants.

Refinement comes from stronger defaults and explicit hierarchy—not from adding a new knob for every edge case.

Tooling follows the model.

Storybook can accelerate controls and generated docs, but it will not supply missing design decisions. Pilot the content structure first.
