Tadoku Paper API study · v12

Technical inspiration, not visual inheritance

Buttons have appearance. Elements have meaning.

Shadcn’s strongest lesson is not a particular border radius or Tailwind class. It is the separation of a reusable variant recipe from the element that receives it. Paper can retain that idea while owning its class-first API and sharp Bookplate appearance.

Navigation uses a link. An operation uses a button. Either element may share the same visual recipe, but styling must never overwrite its semantics.

01 · Current convention

How the shadcn Button API is shaped

Shadcn combines a React component with an exported variant recipe. The component handles button markup; the recipe can style another element without forcing button behavior onto it.

React component

Button variants

Shadcn currently exposes visual variants through a typed prop.

<Button variant="default">Save</Button>
<Button variant="outline">Cancel</Button>
<Button variant="ghost">Close</Button>
<Button variant="destructive">Delete</Button>
<Button variant="link">Learn more</Button>
Important vocabulary difference

Shadcn “default” is visually primary

Shadcn’s default variant is normally the filled emphasis. Paper has already assigned default to the neutral action and primary to the emphasized action. We should borrow the architecture, not its names blindly.

02 · Link semantics

Can a link be a button?

It can look like one. It should remain an anchor in the DOM. Base UI’s Button intentionally enforces button semantics, so shadcn’s Base UI implementation tells consumers to style the anchor with the exported recipe instead.

Correct · navigation

An anchor with button appearance

Continue to forms → 
import { buttonVariants } from "@/components/ui/button"

<a
  href="/contests"
  className={buttonVariants({ variant: "default" })}
>
  Browse contests
</a>
Incorrect · semantic disguise

A Button forced to render an anchor

Do not compose this 
// Avoid with the Base UI Button.
// It applies role="button" and button keyboard behavior.
<Button render={<a href="/contests" />} nativeButton={false}>
  Browse contests
</Button>
Paper direction: export one buttonClassName() recipe for buttons, anchors, and router links. An optional LinkButton may exist, but it must render a real anchor and must never wrap Base UI’s Button primitive.

03 · Forms

Form buttons need explicit jobs

A submit button submits, a cancel button performs an ordinary action, and a React Hook Form reset should normally call methods.reset(). Their visual hierarchy follows intent rather than DOM order.

Interactive form specimen

Paper React API 
<form onSubmit={methods.handleSubmit(save)}>
  <Button type="submit" variant="primary">
    Save log
  </Button>

  <Button
    type="button"
    variant="default"
    onClick={() => methods.reset()}
  >
    Reset changes
  </Button>

  <Button type="button" variant="ghost" onClick={close}>
    Cancel
  </Button>
</form>

Rule: Paper’s Button defaults to type="button". A form submission must say type="submit" explicitly, matching Base UI’s guidance and preventing accidental submissions.

04 · State composition

Loading belongs to both APIs

The component API supplies safe behavior; the class API remains usable without an import. Neither API should make the visible label or accessible name disappear.

React component 
<Button variant="primary" loading>
  Saving log
</Button>

// Output includes:
// class="btn primary loading"
// aria-busy="true"
// disabled
Raw class recipe 
<button
  type="button"
  className="btn primary loading"
  aria-busy="true"
  disabled
>
  Saving log
</button>

05 · Proposed Paper contract

Borrow the recipe architecture

Paper should expose one typed recipe function, one public CSS vocabulary, and thin semantic React adapters. They are three entrances to the same implementation—not separate styling systems.

06 · Primitive boundary

Base UI replaces Headless UI; it does not wrap it

Both libraries solve the same underlying problem: unstyled accessible behavior. Layering them would duplicate roles, focus management, portals, hidden form inputs, and event handlers.

Legacy applications Legacy ui API and styles Headless UI behavior React
→
Migrated applications Paper API, recipes, and tokens Base UI behavior where needed Native HTML where sufficient React
QuestionDecision
Can both packages exist in the repository?Yes. Legacy apps bring Headless UI through ui; Paper consumers bring Base UI through paper-ui.
Can one component use both?No. Choose one behavior primitive and one owner for focus, state, and DOM semantics.
Should Paper expose Base UI directly?No. Apps consume the Paper API so the primitive layer can evolve without an application rewrite.
Do simple Paper buttons need Base UI?Usually no. Native <button> already supplies the correct semantics.
Where is Base UI valuable?Dialog, menu, popover, combobox, autocomplete, custom select, tabs, tooltip, and other difficult interaction patterns.
When is Headless UI removed?Per application at its Paper cutover, then from the repository after the last legacy consumer is gone.

07 · Recommendation

The part worth copying is the separation of concerns

Paper owns meaning, styling, and API. Base UI owns difficult interaction behavior. Shadcn remains a source of technical patterns and comparative examples, not a generated foundation or public dependency.
  • Use native HTML for Button, Link, Input, TextArea, and other straightforward controls.
  • Use Base UI directly inside Paper for complex primitives.
  • Export public recipes independently of React components.
  • Keep links as anchors even when they look like buttons.
  • Require explicit form button types.
  • Preserve loading semantics in both the class and component APIs.
  • Do not expose Base UI or Headless UI types as Paper’s public contract unless unavoidable.
